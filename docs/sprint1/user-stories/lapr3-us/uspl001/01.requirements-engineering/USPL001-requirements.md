# USPL01 - Create a domain model

## 1. Requirements Engineering

### 1.1. User Story Description

As a Product Owner, I want the domain model to be created.

### 1.2. Customer Specifications and Clarifications 

**From the specifications document:**

>	This model will be an essential communication between all the stakeholders.

>	The domain model diagram is a "dynamic" document, which should continuously reflect the stakeholders' shared understanding of the domain. 

**From the client clarifications:**

### 1.3. Acceptance Criteria

* **AC1:** The data model should cover the activity of the railway system operation.
* **AC2:** A basic model is expected, shared in Visual Paradigm or in the GitHub documentation (PlantUML).
### 1.4. Found out Dependencies

### 1.5 Input and Output Data

**Input Data:**

* System requirements and clarifications provided by the Product Owner.
	
**Output Data:**

* Domain Model diagram (Visual Paradigm or PlantUML format).


### 1.6. System Sequence Diagram (SSD)

**This user story does not directly involve system interaction (no actor ↔ system messages).
The activity is conceptual and performed by the development team to produce documentation, not executable functionality..**

### 1.7 Other Relevant Remarks

* The domain model is a living document, evolving with new requirements.
* It forms the foundation for all future data and business modeling.
* Changes to the domain model should be tracked via version control (e.g., Git).
* Visual Paradigm (.vpp) or PlantUML (.puml) versions must be included in the repository for transparency.
* Collaboration and review with the Product Owner are essential to maintain shared understanding.
